# 抖店上货引擎 · 设计说明

## 一、为什么不用影刀那套做法

你现在的影刀流程是「画布拖块」：打开网页 → 设置变量 → 打开文件 → 获取元素 → 列表循环。
它能跑，但有三个绕不开的毛病：

| 影刀画布 | 本引擎（步骤表 + 定位库） |
|:--|:--|
| 流程存在私有格式里（`.flow.json` 是加密的，实测解不开） | 流程是一份 **JSON 步骤表**，能 diff、能版本管理、能贴给 AI 改 |
| 改一个字段要重新拖块、重新对齐 | 改一行 JSON |
| 中途失败只能整段重跑 | 每步落 `state.json`，**断点续跑** |
| 定位写死在元素选择器里，改版即碎 | 定位集中在 `selectors.json`，**按文本/占位符**，改版只改一个文件 |
| 一台机一个流程 | 同一份步骤表可跑 N 个商品 / N 个店铺 |

一句话：**影刀是「拖动一个流程」，这里是「一份数据 + 一个执行器」**。
批量上货的本质是「同一套动作 × N 个商品」，后者天然更省事。

## 二、文件

```
上货引擎/
  selectors.json       定位库（按文本/占位符，禁止写死混淆 class）
  read_products.mjs    读：商品列表 + 单个商品全字段（已实测跑通）
  fill_draft.mjs       写：按 JSON 填表 → 只存草稿（未实现，见下）
  out/                 产物（products.json / product_detail.json）
```

## 四、写操作的红线（当前刻意没做）

`fill_draft.mjs` 未实现，原因是三条必须你先点头：

1. **抖店的「发布商品」是立即生效的**，没有二次确认弹窗缓冲。
2. 写操作会碰真实店铺（保证金、审核、违规风险都在真店上）。
3. 任务书红线：不对真实店铺发写操作，除非指定一件商品且能一键还原。

**建议的落地顺序**：
```
① 先用「保存草稿」跑通填表（草稿不生效、可删）  ← 安全
② 草稿核对无误后，手动点一次「发布商品」        ← 人工闸门
③ 确认整套流程无副作用后，再放开自动发布
```

## 五、下一步要填的三个洞

| # | 洞 | 影响 | 怎么补 |
|:--|:--|:--|:--|
| 1 | **类目 三级路径 → cid 对照表** | 没有 cid 就进不了表单，只能看到 AI 创建入口 | 逐个类目在后台选一次，抓 URL 里的 cid；或找类目树接口 |
| 2 | **类目属性必填项按 cid 不同** | 家具要品牌/材质/重量等 9 项，换类目全变 | 每个类目抓一次「必填项进度」清单 |
| 3 | **16 列模板缺 6 个必填**（运费模板、重量、售后政策、发货模式、发货时间、库存计数） | 纯出表导入走不通 | 从一个已发布商品抓这套值，做「店铺默认模板」复用 |
