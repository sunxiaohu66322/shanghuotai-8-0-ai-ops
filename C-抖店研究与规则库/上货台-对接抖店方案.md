# 上货台 → 抖店 对接方案（实测版）

> 2026-10-29 · 全部结论来自本机实测，不是文档推测。凡未测的都标了「未验证」。

---

## 一、先看清上货台现在是怎么「送货到微信小店」的

```
上货台.exe (PyQt6)
  └─ tab_wx.py  ──►  wxserve.py  ──►  微信小店自建上货台\app.py  (1569 行 HTTP 服务)
                                              │
                                              └─►  wxapi.py  ──►  api.weixin.qq.com
                                                   直连官方 OpenAPI
```

**关键事实：上货台自己不碰微信接口。** 它只是把 `微信小店自建上货台` 这套 Web 服务**在进程内**拉起来（`wxserve.SixtyWeb`），再内嵌一个 WebEngine 显示。

所以「给上货台加一个抖店」不等于改微信那套，而是**再加一条并列的投递链**。

微信这条链能通，靠的是三件东西：
1. `wxapi.py` 里有 AppID/AppSecret → 拿 `access_token`
2. 官方接口齐全：`product/add`、`category/all`、`img/upload`
3. 图片先上传到微信素材库换 URL，再填进商品

---

## 二、抖店为什么不能照抄微信这条路

| 项 | 微信小店 | 抖店 |
|:--|:--|:--|
| 自研后台 | 填了就有 | **要软件著作权证书 + 1–3 工作日审核** |
| OpenAPI | 已通（本机实测） | **拿不到**（无软著，权限审批过不了） |
| 只能走 | 接口 | **真实页面（CDP）** |

**结论：抖店这条链的「手」不是 HTTP 客户端，而是一个已登录抖店的浏览器。**

## 三、抖店新建商品的真实入口（实测，纠正三个误解）

### 3.1 商品管理页**没有** Excel 批量导入新建

实测 `/ffa/g/list` 页全部按钮：

```
新建商品 / 批量修改 / 批量下架 / 批量新建渠道品 / 发布相似品 / 快速发布 / 导出查询商品
```

**没有「Excel 导入」这一项能用来新建。** 之前看到的「Excel 导入」在「更多操作」里，进去是**批量优化（改已有商品）**。

> 这条直接否掉了一个想当然的方案：**别指望像微信那样出一张表就批量上架。**

### 3.2 新版 create 页不给你手选类目

```
/ffa/g/create            → 只有「商品材料 + 商品主图 + 商品详情 + 商品标题」四块
                           接口字段 select_category_limit = "not_support_manual_select"
/ffa/g/create?cid=<cid>  → 才渲染完整表单（76 个字段）
```

实测 AI 创建页的完整动作链（`crawl2/old-create.json` 抓的页面原文）：

```
① 上传 *商品主图（1 张正面图 + 最多 4 张辅助图）
② 上传 *商品详情 图片
③ 填 *商品标题（0/60，需含商品名 + 材质/功能/特征）
④ 点「确认信息，继续生成」  ← 系统在这里替你把类目定下来
```

**这就是你说的「上传主图+标题，系统自动分类目」—— 实测确认成立，你没记错。**

## 四、选定路线：三条里选第三条

| 路线 | 做法 | 判定 |
|:--|:--|:--|
| **A 16 列 Excel 批量导入** | 上货台已有 `doudian.py` 能出这表 | ❌ **只改不建**，无法用于上货 |
| **B CDP 填 cid 表单（76 字段）** | `?cid=` 直开完整表单 | 🟡 可行但脆：76 个字段 + 类目要提前定死 |
| **C AI 创建 + 校验类目 + 存草稿** | 传图 + 标题 → 系统定类目 → 补价/库存 → 草稿 | ✅ **选它** |

**为什么选 C：**

1. **它绕过了「先定 cid」这个死结** —— 你不需要先知道家具挂在哪个末级 cid，系统替你猜。
2. **它和你的既有数据吻合** —— 上货台手里有图（本地绝对路径）+ 标题（已改写选的版本），正好是 C 需要的两样输入。
3. **它天然是草稿** —— AI 生成出来的就是草稿态，不会直接上架。

**C 的风险（必须说清）**：系统猜的类目可能猜错（比如把茶台猜成「桌子」而不是「茶几」）。所以第 ⑤ 步必须做**类目白名单校验**：只接受 一级 ∈ {家具, 户外装备, 家装灯饰光源, 居家日用}，否则停下来报警，不硬推。

## 五、已经做完的东西

### 5.1 抖店 16 列导出：38/38 全过（修了 1 个真 bug）

```
F:\pyenvs\douyin\Scripts\python.exe 上货台\_验_抖店16列.py
→ 通过 38 · 失败 0
```

| 修了什么 | 原来 | 现在 |
|:--|:--|:--|
| **SKU 拼单价为空**（真 bug） | SKU 自身无价格就留空 → 抖店必填，整行导入失败 | 回落到商品最低价，并逐条 warn 写明「回落自 X」 |
| 断言假阳性 | 「原图不许出现在任何一行」 —— 但同一张图被多 SKU 共用是合法数据 | 判据落到**被替换的那一个 SKU 的那一行** |

实测该商品：234 个 SKU，其中 **134 行价格为空**已回落 —— 这种数据如果不修，导进抖店就是整批失败。

### 5.2 送货计划生成器

```
F:\pyenvs\douyin\Scripts\python.exe 抖店研究\engine\mk_plan.py --pid 1526
→ 标题: 新中式茶水柜移动茶台家用小茶桌带轮功夫茶几茶具烧水一体
→ 主图 9 张 / 详情 20 张 / SKU 234 个
→ crawl3\plan-1526.json
```

它负责从 `v3.db` 拿**图片本地绝对路径**（这个只有 python 侧拿得到）和标题优先级，node 侧只管填页面。

### 5.3 送货引擎（node）

```
node 抖店研究\engine\dd.mjs cats          拉类目白名单
node 抖店研究\engine\dd.mjs push --pid 1526 [--dry]   推一件到草稿
node 抖店研究\engine\dd.mjs audit         读回草稿，逐件查完整度
```

三条硬约束写死在代码里：
- **从不点发布**，只到草稿
- **自动扫端口** 9224 + 9223..9299（ego 重启会丢端口，不写死）
- 所有 eval 都带超时（上一版页面内 fetch 无超时，挂死过两次）

```powershell

  --remote-debugging-port=9224 --user-data-dir="F:\ego-ud-link"
```

⚠️ **② 要先把当前 ego 全部关掉**（profile 被锁），所以 ① 更安全。
