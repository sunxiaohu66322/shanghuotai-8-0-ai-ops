## 2. 两处必须先修的「口径打架」（这是本次审计最重要的发现）

### 2.1 2.5 照片墙不看 `main_image_id` → 4.1 确认后它看不见

```python
# server/library.py:172  local_image(pid)
for role in ("main", "", "detail", "sku"):
    ... where product_id=? and role='main' ... order by sequence    # 取第一条本地存在的
```

**它按 sequence 排序取第一张，完全没读 `v3_product.main_image_id`。**

而 `packaging.build_row()` 出表是**认 main_image_id** 的：

```python
# server/v3/packaging.py:97
main_id = p.get("main_image_id")
ordered_main = sorted([i for i in imgs if i["role"] == "main"], key=...)
main = 按 main_id 命中的那张
mains = [_pick_url(main)]
```

**后果（必然发生，不是可能）**：4.1 里修补第 2 张主图 → `import_new` 生成 seq=max+1 的候选 → `approve` 只挪 `main_image_id` →
**出表用新图 ✅，2.5 照片墙仍显示旧图 ❌**。

这正是用户点名的"别你这边改了，2.5 那边看的还是没改"，而且方向还更糟：**出表已经换了、照片墙没换，人会以为没成功。**

**修法（只读层，1 处）**：`Library.local_image()` 先按 `v3_product.main_image_id` 精确取，取不到再退回现在的 sequence 逻辑。
风险：2.5 部分商品的缩略图会换成"已确认的新版"——**这正是期望行为**，且不写库。

### 2.2 `import_new` 会覆盖精筛结论

```python
# server/v3/images.py:226
store.set_product_status(conn, pid, "image_handoff")
```

→ 4.1 每存一次版本，就会把第三步的 `passed / blocked / pending / review` 改成 `image_handoff`。
**修法**：`import_new(..., keep_status=True)` 新增参数（默认 False 保持旧行为，4.1 传 True），并在自检里断言"存版本前后 `v3_product.status` 不变"。

| 项 | 风险 | 处置 |

### 4.2 遮罩与参数往哪存（现状没有字段）

`v3_image` 有 `note TEXT`，但它是自由文本、会被人工改、不可索引。三个方案：

| 方案 | 做法 | 评价 |
|:--|:--|:--|
| A 塞 note | `note` 里放 JSON | **不推荐**：不可查、易被覆盖、失败率统计做不了 |
| **B 新增 `v3_image_edit`（推荐）** | 6–9 列：`edit_id / image_version_id(指向 v3_image.image_id) / product_id / mask_path / method / params_json / quality_json / elapsed_ms / state / created_at` | 单表、可索引、可统计；**回滚 = DROP TABLE**；不是"第二套版本库"（版本仍是 v3_image 的行），只是**编辑动作取证** |
| C sidecar JSON 文件 + note 存路径 | 不建表 | 可行但查询困难 |

**推荐 B，且默认对业务逻辑"只写不读"**（只有 4.1 自己读来做状态徽章），这样即使将来不想要也能安全删掉。

## 5. 接口契约（阶段 C/D 直接照此接，不再改设计）

```python
# ---- 只读（app/v3img.py，全部走 mode=ro）----
list_mains(pack_code='', state='', q='', only_local=True, limit=2000) -> list[dict]
   # 每行：image_id, product_id, sequence, title, pack_code, path, exists,
   #       is_main_pointer(==v3_product.main_image_id), status(v3_image.status),
   #       edit_state(none|draft|repaired|failed|confirmed), n_pending_regions,
   #       ocr_ok, ocr_boxes, w, h

image_detail(image_id) -> dict        # 含全部 v3_image 字段 + OCR 框 + 编辑历史

# ---- 写入（bridge，全部走 _wrap 可写连接）----
m_draft_save(image_id, mask_png_bytes, regions_json, note='') -> {'ok', 'draft_path'}
m_repair(image_id, regions, method='telea', radius=3, save_draft=False) -> 
   {'ok', 'version_image_id', 'path', 'sha256', 'elapsed_ms', 'inspect':{...}, 'verdict':'ok|review|bad'}
m_repair_confirm(product_id, version_image_id) -> 复用 images.approve()，返回 previous_main_image_id
m_repair_revert(product_id) -> 复用 images.revert()
m_repair_reject(product_id, version_image_id) -> 复用 images.reject_candidate()
m_ocr_boxes(image_id) -> boxes_of()
```

**铁律（写进函数头注释，不只写在文档）**：
1. 4.1 只接受 `role='main'` 的 image_id，其它角色直接拒绝并说明原因。
2. 原图 `appearance`：任何写操作都不得触碰 `original_local_path` 指向的文件（阶段 B 已有 `UnsafePathError` 守卫，沿用）。
3. `confirmed` 才进发布：出表读 `main_image_id`（现有），故"确认"= `approve`；未确认的候选永不成为 `main_image_id`。
4. 修补 `verdict != 'ok'` 的版本**不阻止确认，但必须在界面上写清"自动检查判为需复核"**，并记入 `v3_image_edit.quality_json`。
