## 2 【第一】粗筛错误的真正根因

### 2.0 现象回顾

```
库内 205 件
  分级    C=104 · (空)=40 · B=34 · 排除=27 · A=0
  店铺    (空)=145 · 未知=24 · 旗舰店=18 · 专卖店=14 · 工厂店=4
```

### 2.1 根因① 库里存的是旧结果 —— 当前代码从没在这批数据上跑过（最主要）

**用当前代码逐条重算，结果与库内存储值大面积不符：**

```
分级        不一致 156 / 205   （76%）
店铺类型    不一致 194 / 205   （95%）
```

**重算分布 vs 库内分布：**

| | 库内 | 当前代码重算 |
|:--|:--|:--|
| 分级 | C=104, 空=40, B=34, 排除=27, **A=0** | B=113, 排除=88, **A=4** |
| 店铺类型 | 空=145, 未知=24, 旗舰店=18, 专卖店=14, 工厂店=4 | unknown=79, 无=11, **flagship=70, exclusive=34, factory=6, authorized=5** |

**★ 三条直接结论：**

1. **A=0 不是规则算不出 A** —— 当前代码在这批数据上能算出 **4 件 A**。库里没有 A，是因为**从没重算过**。
   ```
   [C→A] 亚明户外工程灯具工厂店 | 亚明400W高亮LED投光灯防水工业风照明灯IP66质保
   ```
   这件库内是 C，重算是 A。它的店名含「工厂店」→ 当前代码认得出。

2. **145 件「店铺类型为空」里，134 件店名是有值的** —— 只有 11 件是压根没采到店名。
   ```
   店名本身为空（根本没采到） : 11
   店名有值但没判出类型       : 134
   ```
   **而这 134 件用当前代码重算，能认出 115 件**（flagship 70 + exclusive 34 + factory 6 + authorized 5）。
   **所以「空」不是因为认不出，是因为写库时用的那版代码认不出。**

3. **24 件「店铺类型未知」是旧代码写进去的字面值** —— 当前 `parse_store_type()` 返回的 code 只有
   `flagship/official/exclusive/authorized/factory/personal/unknown`，
   **不会产出「店铺类型未知」这个中文串**。那是外层包装文案被写进了字段。

> **判据**：`parse_store_type()` 返回 `(code, cn, rule)` 三元组；写库时应取 `code`。
> 库内出现的「工厂店/厂家直销」「店铺类型未知」是 `cn`（中文显示名），说明**写库时取了第二项**。
> 这解释了为什么库内值是中文而重算值是英文 code —— **两版代码口径不同**。

### 2.2 根因② 品牌闸门把「店名命中」当成「标题命中」（误杀主因）

**命中位置分布（重跑 `judge_brand` 全部 205 件）：**

```
标题          70 件
店铺名        52 件   ← ★ 只在店名里命中
标题/店铺名     6 件
title/shop     3 件
（无命中）     74 件
```

**★ 52 件商品只在店铺名里命中品牌词。** 而主人的定级规则看的是**标题里有没有品牌名**：

> 「标题和店面都是旗舰店的就是 C 级，都没有的就是 A 级」

**实例（决定性）：**

```
命中词=探露   where=店铺名   registry_only=True
店铺：回头客2万探露运动户外旗舰店
标题：户外折叠椅子便携式超轻折叠凳子钓鱼椅露营靠背坐椅野营板凳马扎
      ↑ 标题里没有「探露」
结果：被判 protected_brand → 排除
```

**按主人规则，这件标题无品牌名 → 店属旗舰店 → 应该是 B，不该被排除。**

**这就是「品牌排除闸门与 A/B/C 定级冲突」的确切机制：闸门用的字段（标题+店名）比定级规则用的字段（标题）宽，前者把后者能救的商品提前杀掉了。**

### 2.3 根因③ 品牌词库子串误切 + 产品类型词混入

**命中的品牌词 TOP（重算 205 件的真实频次）：**

```
牧高笛 16 · JEEP 13 · 奥克斯 8 · 骆驼 4 · 原始人 4   ← 真品牌，判定正确
海狗 3 · 探露 3 · 卡诺 2 · 疆屿 2 · 德普 2 · 傲威 1  ← 需逐条判定
山人 2 · 骑士 1 · 正火 1 · 牧野 1                   ← 主人已裁定「都是品牌，保留」
MUJI 2 · TCL 1 · 飞利浦 1 · 欧普照明 1 · 特步 1      ← 真品牌
```

**两类明确误杀：**

| 类型 | 实例 | 说明 |
|:--|:--|:--|
| **产品类型词被当品牌** | `海狗`（3 次） | 「海狗椅」是克米特椅的一个款式名，是**产品词**。标题 `Abenaki户外海狗椅…` 里的真品牌是 `Abenaki`（未被命中） |
| **子串误切** | `卡诺`（2 次） | 从 `探卡诺` 中间切出；`探卡诺` 本身才是品牌名 |
| **子串误切** | `傲威`（1 次） | 从 `比尔傲威` 中切出 |
| **类目词被当品牌** | `老板`（1 次） | 从「办公老板椅」切出，命中「老板电器」 |

**★ 一条关键限定**：`registry_only=True` 共 **76 件**，**全部 protected_brand 都是 registry_only**。
即：**这些命中只说明「这个词在 19023 条收录表里」，没有任何一项是已确认侵权。**

**而配置项 `brand_gate.wordlib_brand_exclude=true` 把这 76 件直接判为「排除」。**
原文提示词写得很清楚：「收录只说明这个词是登记过的品牌名，**不等于已确认侵权**」——
**代码却在同一段里就把它当成了排除理由。这是自相矛盾的一处。**

### 2.4 根因④ 工厂店漏识别 —— 店名里混进了平台徽章

**店名以「工厂 / 厂 / 厂家 / 制造」结尾、但当前代码认不出的，10 件：**

```
回头客300万好货严选工厂       → unknown
回头客9000万天天特卖工厂      → unknown
皓明户外照明工厂              → unknown
回头客10万朗鹏led灯饰厂       → unknown
中山灯具酒轨照明工厂          → unknown
极有家朗鹏led灯饰厂  (×4 件)  → unknown
千机灯饰厂家                 → unknown
```

**根因是两层叠加：**

1. **`store_type_rules.factory.match` 只收了完整词**（`工厂店 / 厂家直销 / 源头工厂 / 工厂直发 / 厂家直发`），
   **不收「工厂」「厂」「厂家」结尾** —— 而后者是淘宝店名更常见的写法。
2. **采集时把平台徽章拼进了店名**：`回头客300万` / `极有家` / `10年老店` / `16年老店` / `11年老店` /
   `回头客1万` / `回头客2万` / `回头客4万` / `回头客5万` / `折800的店`。
   **这是卡片 DOM 抓取时把徽章元素一并读进了店名 —— 属采集层问题，不是规则层。**

**影响**：这 10 件按主人规则应为 **A**（工厂店 + 标题无品牌名），实际落成 B 或未知。

### 2.5 边界：无效链接

```
「排除」档理由归因：品牌闸门 79 · 无效链接 13
```

**13 件因「解析不出 12 位数字商品 ID」被排除。** 卡片阶段拿不到商品 ID 是合理的
（搜索页卡片不总带 ID），但**这些件是否本该进入下一轮，当前无法判断** ——
它们既没进候选也没留待办，属于**静默丢弃**。建议改为「低优先级待补」而非直接排除。

## 3 【第二】细筛的真实能力

### 3.1 五层漏斗实际执行了什么

```
第0层  选品任务定义       selection.parse_task_text()      自然语言 → 12 个字段
第1层  候选池             selection.load_candidates()       从 products 取 or 外部 rows 传入
                          selection.build_clusters()        认款聚类（三条判据）
第2层  硬性淘汰           hard_filters.apply()              5 道闸门
第3层  12 维评分          scoring.score()                   12 维 + 置信度 + 缺失剔除
第4层  AI 判断            ai_selector.analyze()             ★ 见 3.4
第5层  报告               report.py                         A/B/C + 为什么不做
```

**12 维清单（`scoring.py:457`，实测确认）：**

```
市场需求 · 增长趋势 · 竞争强度 · 利润空间 · 客单价 · 同款泛滥
差异化空间 · 内容可销售性 · 售后风险 · 供应链友好度 · 品牌风险 · 可复制性
```

### 3.2 ★ 哪些评分是真实数据、哪些是推测（本轮最重要的量化结果）

**直接查库：205 件商品里，细筛依赖的字段非空情况——**

| 字段 | 非空 / 总数 | 影响哪一维 | 后果 |
|:--|:--:|:--|:--|
| `cost_price`（进价） | **0 / 205** | 利润空间（15 分） | **必然走 `default_cost_ratio` 猜 → confidence=low** |
| `sales_num`（销量） | **0 / 205** | 市场需求（10 分） | 只能从卡片"销量文案"解析，拿不到数字就剔除 |
| `review_count`（评价数） | **0 / 205** | 市场需求 | 同上 |
| `growth_rate`（增长率） | **0 / 205** | 增长趋势（10 分） | **无时间序列 → 必然算不出** |
| `same_style_count`（平台同款数） | **0 / 205** | 竞争强度（10 分） | 只能靠本地聚类，样本 205 条时簇数有限 |
| `brand_type` | **0 / 205** | 品牌风险（5 分） | 走 `hard_filters` 现算，不依赖此列 |
| `weight_kg` | **0 / 205** | 售后风险（7 分） | 只能按类目基准估 |
| `shipping_cost` | **0 / 205** | 利润空间 | 走 `shipping_cost` 默认 12.0 元 |
| `shop_type` | **60 / 205** | 硬过滤（品牌/店铺闸门） | 145 件缺 → 店铺相关判定失效 |
| `select_grade` | **165 / 205** | — | 40 件未定级 |
| `search_keyword` | **205 / 205** | — | 唯一全满的字段 |

**★ 结论：12 维里 4 维（市场需求 10 + 增长趋势 10 + 竞争强度 10 + 利润空间 15 = 45 分）
在当前数据条件下必然落在「算不准」区间。**

**利润那 15 分的具体路径**（`hard_filters.compute_profit`）：

```
① 有真实 cost_price      → confidence=high   （库内 0 件走这条路）
② 有同款簇              → 用簇内最低价当进价 → confidence=mid
③ 都没有                → 进价 = 售价 × default_cost_ratio(0.5) → confidence=low ← 猜的
```

**库内 `cost_price` 全空 → 只能走 ② 或 ③。** 而 `compute_profit` 对 low 的处理是
**只警告、不淘汰**（`hard_filters.py:339`），这一点是对的（避免拿假数字杀人），
但**报告里那一项分数实际意义有限**，必须看 `confidence` 才不漏读。

### 3.3 ★ 粗筛与细筛是否真正衔接 —— **没有衔接**

| | 粗筛 | 细筛 |
|:--|:--|:--|
| 入口 | `POST /api/prescreen` → `prescreen.screen_cards()` | `/selection` 页 → `selection.run()` |
| 引擎 | `prescreen.py`（新体系，两信号表） | `hard_filters.py` + `scoring.py`（12 维） |
| 定级依据 | 标题品牌名 × 店铺类型 → A/B/C/排除 | 12 维加权分 → S/A/B/C |
| 品牌判断 | `prescreen.judge_brand()`（19023 词库） | `hard_filters` 自己的品牌逻辑 + `brand_rules.json` |
| 店铺类型 | `prescreen.parse_store_type()`（读 `selection_profile.json`） | 未见等价调用 |
| 数据源 | `products` 表（写入方） | `products` 表（读取方） |

**事实：两条链路共用数据库，但各有一套独立实现，粗筛的 `select_grade` / `shop_type`
没有被细筛读取或继承。** 同一个「品牌风险」概念在两边是两套代码两套阈值。

**风险**：粗筛说 A 的商品，细筛可能因另一套品牌逻辑判为高风险；反之亦然。**用户看到的两个页面口径不一致。**

### 3.4 AI 判断层的真实状态

- `ai_review()`（粗筛内）**已接入**，实测可跑（`batch=4 / timeout=420`），失败自动退回规则。
- `ai_selector.analyze()`（细筛第4层）**接入同一端点**，但见 §6 第 2 条 —— **它的速度特征决定了它只适合短判定**。
- **两处 AI 调用各写各的提示词**（`prescreen._ai_prompt()` vs `ai_selector.PROMPT_TEMPLATE`），**口径未统一**。

### 4.2 ★ 实发 6 条请求，看它到底输出什么

| 输入 | 耗时 | tier | triggered_by |
|:--|:--:|:--|:--|
| 安装一个软件 | 0.13s | low | rule_mechanical |
| **判断这家店是不是工厂店：亚明户外工程灯具工厂店** | 1.82s | **max** | laya |
| **这个商品标题里有没有品牌名：TCL太阳能露营灯** | 1.62s | low | laya |
| 把下面 50 件商品按 A/B/C 分档 | 1.53s | high | laya |
| 帮我分析一下这批户外椅的市场竞争度 | 0s | high | rule_cognitive |
| 重新做一遍 | 1.26s | low | laya |

**完整输出 schema（实测原文）：**

```json
{"tier":"low|high|max|critical",
 "triggered_by":"rule_mechanical|rule_cognitive|laya",
 "labels":{"Q1":bool,...,"Q7":bool},
 "probs":{...}, "yes":[...], "ms":N,
 "intent":{"op":"none","tier":null,"span":"...","polarity":"neutral",
           "stage":"no_anchor","void_reason":"vocabulary_gap"}}
```

### 4.3 ★ 结论：**不能直接当作商品分类器**

**三条决定性证据：**

1. **输出里没有任何分类字段。** schema 只有 `tier`（档位）+ 7 个布尔 `Q` 标签 + `intent`。
   **没有「品牌名是什么」「店铺类型是哪类」「该判 A/B/C」这类输出槽位。**

2. **给它分类问题，它回答的是「这活费不费脑子」。**
   ```
   输入：判断这家店是不是工厂店：亚明户外工程灯具工厂店
   输出：tier=max  Q4=true  prob=1.0
   ```
   `tier=max` 的意思是「这个任务需要最高档推理」，**不是「这是工厂店」**。
   拿它当分类器用，等于把「难度评级」误读成「分类结果」。

3. **★ 商品域词汇完全不在它的词汇表里。**
   **6 条请求的 `intent` 全部是 `stage=no_anchor, void_reason=vocabulary_gap`** ——
   连「安装一个软件」这种明确任务也是。说明意图解析层**认不出这些输入属于哪一类操作**，
   直接落到「无锚点 / 词汇缺口」。
   `Q4=true`（亚明那条）是模型对「这句像是在问需要仔细判断的事」的粗判，**不是对工厂店的识别**。

### 4.4 若要用它做商品分类：需要什么

| 项 | 判断 |
|:--|:--|
| 直接调用现有 `/judge` 做分类 | **不可行** —— 无输出槽位、词汇域不匹配 |
| 需不需要重新微调 | **需要**。它是「档位判定」目标微调的（803MB），训练目标与商品分类无关 |
| 微调数据从哪来 | **本项目正好有**：205 件真实商品 + 店名 + 标题，**且其中 165 件已有 `select_grade`**（虽属旧版结果，但可作初筛标签起点） |
| 延迟 | 规则层 0ms / 模型层 1.3–1.8s（单条）。**批量 205 件 ≈ 4–6 分钟**（若走模型全部） |
| 资源 | 权重 803.6MB，与主模型相比极小；当前占用未测（未做资源观测，**标为待验证**） |

### 4.5 关于「疑难分流」的可行性

**它现在能做的、与选品沾边的唯一一件事**：判「这条任务需要多少推理档位」。
把这用在选品上，唯一合理的用法是：

> **在调用云端大模型前，先用它判这条商品需不需要送去 AI 复核** —— 简单件走规则、疑难件才走云模型。
> 这能省调用次数，**但它不产生分类结论**。

**这个用法本轮未验证**（需要先有「什么算疑难」的定义，而定义又依赖人工标签，见 §5）。

## 5 【第四】对照验证设计（方案已定，**未执行**）

### 5.2 ★ 为什么本轮**没有**执行 B / C

**用户明确要求：没有人工确认的正确标签，不得宣称准确率提高。**

- 因此 B / C 跑出来只能得到**分布差异**，得不到「谁更准」

**方案 C 还多一层阻塞**：Laya 的 `tier` 与「商品是否疑难」之间没有已建立的映射。

### 5.3 要让它可执行，最少需要（见 §6）

1. **人工标注一个小样本**（建议 30 件：覆盖 A/B/C/排除 各若干），作为金标准
