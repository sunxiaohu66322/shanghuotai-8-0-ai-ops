# 拼多多手机版数据采集风控触发因素调查报告

> 调查日期：2026-11-10 · 范围：**只读调查**，不操作手机、不改采集程序、不碰 `v3.db`、不发布/修改任何商品
> 缘起：主人拿外部 AI 的《公开资料调查》来问「用手机采集，其他手机号一登进去就『已售罄』，怎么调能少风控，比如把 root 状态屏蔽掉」
> 证据分级：**[事实]** 有官方原文或本机实测出处 · **[推断]** 由事实合理推出 · **[猜测]** 待验证 · **[未证实传闻]** 网上流传、无对照实验
> 一句话立场：**不写"绕过检测"的招，写"少触发"的工程调法**——两者不是一回事。降请求量、拟人节奏、被动读取、异常熔断属于后者；换号洗白、伪造设备、轮换 IP、对抗完整性校验属于前者，本报告逐条说明为什么前者有效、后者无效或反效果。

## §0 先给结论（含三处对提问前提的直面纠正）

**结论 1 ——「已售罄」在本项目里已经有本机实测结论：它是账号级风控，不是通用资料里说的"不能断定"。**
外部 AI 那份通用资料写「单凭页面文案不能直接断定」——对通用场景成立，但**本项目不适用**。本机归档会话 `dsh-A-05-手机拼多多采集-2.0` L119–L122 记着一次真实复盘：AI 先判「售罄=登录态掉了」，主人当场纠正「**售罄不是登录掉了，就是风险账号了，现在恢复正常是因为我换了一个号**」，AI 认错并写明「证据：你换号立刻恢复，登录态没变」。〔**[事实]**，出处见 §1〕
→ 所以主人本轮说的「有些号一登进去就是已售罄，商品数据看不到」= **账号一登录就被判定，商品详情数据被降级/不返回**，是账号维度，不是设备、不是网络、不是商品库存。

**结论 2 ——「把 root 状态屏蔽掉」这条路，本机已经做过，而且帮了倒忙。不能顺着做。**
同一份会话录：L134「六处隐藏全部做完并实测通过」、L142–L143「**是我昨晚装的 Shamiko 卡死了拼多多**（不是手机坏、不是风控）」、L145「**不行，你还要想办法处理。我这个点进一个商品就被风控，就看不到商品信息了**」。即：root/环境隐藏做完之后，先出现 App 打不开，修好之后点进商品仍被风控。〔**[事实]**〕
机制上说得通〔**[推断]**〕：Magisk/Shamiko/隐藏列表、改系统参数、多开、抓包代理本身都是**可被检测的异常面**，隐藏动作会引入新的不一致（注入痕迹、进程/属性矛盾、完整性校验失败），而不是把设备变"干净"。**一台真正干净的手机，不需要隐藏；上隐藏，等于先自证"这台机器有东西要藏"。**

**结论 3 —— 少风控的第一杠杆不在设备层，在「采集方式 > 行为节奏 > 账号卫生」，设备/root 排最后且优先不动。**
本机已经验过一条**零新增请求**的采集路径：L26「真实商品 `goods_id=976338685051` **105 条真实 SKU 一发即中**，全程**只读 hook、零点击、零网络改动**，PDD 进程存活」；`pddsrc\调研-拼多多SKU数据链路-20261018.md` §3.2 把它写成设计原则：「不构造请求，App 自己发 …… **风控：零新增请求，与用户手动浏览完全同流量**」。〔**[事实]**〕
→ 这才是"怎么调能少风控"的正解：**让采集不再产生"额外的、非人的"访问**。设备怎么伪装，都抵不过"你比人多发了 200 个请求"这一条。

## §2 "已售罄"到底可能意味着什么 —— 五种状态怎么区分

沿用外部资料 A–E 五分法，补上**本项目的判别抓手**（"看范围"比"看文案"可靠）：

| 情况 | 性质 | 判别抓手 | 置信度 |
|:--|:--|:--|:--|
| **A 真实库存售罄** | 正常业务 | 只影响**个别商品**；换规格/换店铺/换时间仍稳定；未登录也能看到同状态 | [事实]（协议明载商品页有数量限制） |
| **B SKU 售罄** | 正常业务 | 商品整体在售，**选中某个颜色/尺寸**才不可买；`is_onsale=0` / `quantity=0` 只落在部分 sku | [事实]（`SkuEntity.is_onsale` / `quantity` 字段见链路调研 §1.6） |
| **C 地区/配送限制** | 需核实 | 同账号同设备，改收货地区后变化；常伴"该地区不可配送/不可购买"文案 | [推断] |
| **D 页面/数据异常** | 需核实 | 网络切换、客户端版本、缓存、服务端同步延迟；**页面正常但采集记录异常** → 优先查解析，不查风控 | [事实]（链路调研 §2 已证 H5 预渲染壳 `"skus":[]` 就是空数组） |
| **E 访问限制 / 风控降级** | **本项目重点** | **换号立刻恢复、登录态没变**（本机 L121）；大面积无关商品同时售罄；手动浏览也异常 | [事实]（本机实测）+ [推断]（"降级展示"的具体形态官方未确认） |

**一条最实用的判据**（把外部资料"不绕过"和本项目"要定位"接起来）：
> **只看范围，不看文案。** 单品 → 库存/SKU；同店铺多品 → 店铺/地区；**跨店铺、跨品类、登录后立刻全店售罄 → 账号/会话级**，此时**停止采集**，不要再靠多发请求去"试"出来。

**必须点名的混淆**：`goods.html` 预渲染壳里 `"skus":[]` 是**空数组**，是页面结构，不是"商品卖光了"；采集程序若把 `skus` 为空解析成"已售罄"，会凭空造出一批假售罄。链路调研 §2.1 已在 3,336 个落盘响应体里逐个核过。〔**[事实]**〕

## §3 触发因素：八个方向逐条过

标注口径：**官方** = 用户协议/隐私政策明文；**本机** = 上面 2–5 号留档实测；**行业** = 电商反自动化常见维度、**拼多多未公布、不能认定必然触发**。

### 01 高频浏览与重复刷新 —— 高
- 本机 §8 硬约束原话：「**所有动作必须像人** —— 不要快进快出、不要机械连点。**本会话已因高频操作把账号搞报警过一次**」（主人原话「你这边快进快出又把账号搞报警了」）。〔**本机 [事实]**〕
- 官方口径：协议允许依「用户行为、海量用户数据关系、普通人的正常消费/交易习惯」判断异常。〔**官方**，外部资料 §二 C〕
- 行业推测：短时间连续打开大量商品、连续刷新同一商品、快速换关键词、大量翻页、反复进出详情——都可能进异常判断。**具体次数/时间窗网上流传的固定数字一律 [未证实传闻]**，不写进本报告的调参依据。

### 02 商品详情 / SKU / 库存访问 —— 高
- 反复切换 SKU、反复拉规格面板会产生 `/api/oak/integration/render/sku` 重复请求（链路调研 §1.3）。〔**本机 [事实]**：接口存在〕
- 但**只读 hook 方案根本不点规格面板**：`setRenderResponse(w)` 在首次渲染就拿到全量 `w.sku`（§1.2/§3.1），一次给全，**不需要逐条请求**。〔**本机 [事实]**〕
- → 这一项的"少触发"解法不是放慢点规格，是**不点**。

### 03 自动化点击 / 脚本采集 —— 高（本项目最大的可控变量）
- 官方明文禁止「插件、外挂、机器人、蜘蛛等程序擅自获取内容」「使服务器超负荷」。〔**官方**，外部资料 §二 A/B〕
- 本机实际用过的：`uiautomator dump` / `x_ui.py` 自动 tap / `drive_goods.py` 驱动点商品 / `collect_sku.py` / 无障碍或 root 下的批量点击 / mitmproxy 抓包 / Frida（本机 3 次 SEGV 已判废）/ LSPosed。**自动点击 = 会引入非人节奏**，这正是 §8 那条硬约束的由来。〔**本机 [事实]**〕
- **两个 AI 同时 adb 操作同一台手机会互相打断**，症状是"点了没反应"，容易被误判成"页面卡了/被风控了"。交接文档 §9 明令串行。〔**本机 [事实]**〕

### 04 Root / 模拟器 / 多开 / 环境隐藏 —— 高，但**方向要反过来**
- 本机设备：`1cc23ce7` MI 8 SE / Android 10 / **已 root**（交接 §4）。隐私政策明列采集设备标识符、设备参数、应用信息、传感器、日志。〔**官方 + 本机**〕
- **本机已做过隐藏**：L134「六处隐藏全部做完」→ L143「**Shamiko 卡死了拼多多**」→ L145「点进一个商品就被风控」。〔**本机 [事实]**〕
- 判定〔**[推断]**〕：root 本身是环境信号；**Magisk/Shamiko 隐藏、改参数、多开、分身、修改版客户端、抓包代理**这些"再加工"会制造新的不一致，属于**放大异常面**而非消除。模拟器同理（设备环境不符合正常客户端特征，行业推测）。
- **对主人那句「把 root 状态封闭掉、屏蔽掉」的直接回答**：这台机器 root 是为了装 LSPosed/只读 hook 采全字段（本机 2.0 会话 L125 已确认「没 root 的干净机采不全：图片 URL、视频 URL、SKU 精确价格、商品 ID 全拿不到」）。**所以 root 不能去掉，能去掉的是"多余的伪装层"和"多余的点击/请求"。** 建议做法见 §7.2：不是加隐藏，是**减层**。

### 05 IP / VPN / 代理 / 网络变化 —— 高（但别乱动）
- 官方隐私政策明列 IP、Wi-Fi、基站、运营商。〔**官方**〕
- 本机链路：手机 → SunnyNet VPN 总开关 → PC `mitmdump :2024`；交接 §4 记着「手机没走代理 = 抓包停了 1.5 小时」，且**曾有计划任务「PDD采集链路守护」每 2 分钟 `am start` 拉起 SunnyNet 抢前台**（2.0 会话 L59 已修）。〔**本机 [事实]**〕
- **代理/VPN 本身不能证明触发风控**（外部资料 §一 4 也这么写）。但**网络出口频繁变化、抓包代理长期挂着、请求中断重试过多**是行业里常见的异常维度。〔**[推断]**〕
- 反向提醒：**靠轮换 IP / 换出口来"洗白"属于绕过方向**，外部资料 §四.3 明列不要做，且协议「相同/相近/交叉的 IP、设备、支付、收货信息可能被认定关联用户，统一管理」——轮换反而可能**扩大关联面**。〔**官方 + [推断]**〕

### 06 账号登录 / 会话 / 设备关联 —— **本项目头号因素**
- **本机铁证**：L121 主人「售罄不是登录掉了，就是风险账号了，现在恢复正常是因为我换了一个号」；交接 §8 第 4 条「手机操作前先确认账号状态 —— **已换过一个新账号，别再搞成风控**」。〔**[事实]**〕
- 官方：协议明写注册/登录信息、实名、设备、IP、支付、收货信息**相同/相近/交叉**的账户可能被认定关联用户统一管理。〔**官方**，外部资料 §二 D〕
- 推论〔**[推断]**〕：主人说「其他手机号还是会有封控风险，有些号一登进去就是已售罄」——**这类号很可能是被关联或已有历史标记的号**，不是"新号就安全"。**多账号共用同一台 root 设备 + 同一代理出口 + 同一采集程序 = 关联要素高度重合**，换号只能短期恢复，不能解决根。
- → 少风控的正确动作不是"多备几个号轮着登"，是**一个号、一台设备、一套稳定环境、低请求量、长期不切换**（§7.5）。

### 07 页面缓存 / 客户端 / 数据解析 —— 高，且**最容易被误判成风控**
- 本机实测：`uiautomator dump` 在详情页因自动轮播 + 直播悬浮层**永不 idle**，必报 `could not get idle state`，四种办法全无效。〔**[事实]**，交接文档 §3.4〕
- H5 预渲染壳 `"skus":[]` 空数组、native 页面无 DOM、图片/视频 URL 不在 UI 树里。〔**[事实]**〕
- `format:'json'` 让 `qwen3-vl:2b` 静默返回空 → 看起来像"采不到数据"，实为 OCR 参数 bug。〔**[事实]**〕
- → **先排除解析层，再谈风控**。否则会把程序 bug 当成账号被限，然后去动设备/账号，越动越乱。

### 08 库存 / 地区 / 活动限制机制 —— 高（业务侧，非风控）
- 协议明载：单商品总出售数量、单笔限购、同一用户同类商品限购、活动参与次数、期限等页面限制；平台/商家可取消订单与活动资格。〔**官方**〕
- 本机数据里 `SkuEntity` 有 `limit_quantity` / `is_onsale` / `quantity` 字段。〔**[事实]**〕
- → 见 §2 表 A/B/C，**这几类不需要任何"恢复"，也不该记成风控事件**。

## §4 风控机制：平台可能用哪些维度（不是内部规则，是"官方承认会看什么"）

拼多多**没有公开**评分模型、阈值、"售罄码"。能由官方原文确认的只有"会综合看这些"：

| 维度 | 官方原文出处 | 具体项 |
|:--|:--|:--|
| 账户 | 隐私政策 V4.1.1 / 用户协议 V4.2 | 注册登录、实名、账户信息 |
| 交易 | 同上 | 交易信息、支付、收货、售后 |
| 设备 | 隐私政策 | 设备标识符、设备参数、应用信息、**传感器信息** |
| 网络环境 | 隐私政策 | IP、Wi-Fi、基站、位置、蓝牙、运营商 |
| 日志/行为 | 隐私政策 | 点击、浏览、搜索、分享、交易、时间 |
| 关联关系 | 用户协议 | 相同/相近/交叉的注册/设备/IP/支付/收货 → 关联用户统一管理 |
| 异常判定基准 | 用户协议 | 登录信息、用户行为、海量用户数据关系、**正常消费习惯**、行业惯例 |
| 处置 | 用户协议 | 记录/分析/审计、限制账户功能、关闭权限、中止或终止服务 |

〔全部 **[事实]**：外部资料 §一、§二 已逐条附 [1][2] 官方 PDF 链接〕

**关于"对不同访问者返回不同商品状态"**：机制上可行（服务端按会话/账号下发不同渲染结果，本机的 `render` 响应本就是服务端组装的 `w` 对象）。但**官方没有确认"售罄"是一个风控响应码** —— 标 **[推断]**。〔链路调研 §1 的 `w`/`GoodsResponse.setRenderResponse` 证明响应由服务端整体下发，[事实]〕

**明确不写的三样**：触发阈值、评分公式、解除时间。三者都缺可核验证据，写了就是编。

## §5 影响范围：怎么判断是「单个商品」还是「更大范围」

给一棵不绕过、不多发请求的判定树（**每一步只做观察，不加重访问**）：

```
① 只 1 个商品售罄，其他全正常
     → A 真实库存 / B SKU 售罄 / 解析 bug（先查 §2 D）
② 同一店铺大量商品售罄，别店正常
     → 店铺状态 / 地区配送限制 / 店铺级活动批次
③ 跨店铺、跨品类、登录后立刻"全店/全部售罄"
     → 账号 / 会话级  ← 本项目属这一档（本机 L121 换号即恢复）
④ 换号后立刻恢复、登录态没变
     → 账号级风控 [事实]，不是设备、不是网络
⑤ 换号也不恢复，且手动浏览同样异常
     → 才轮到怀疑设备环境 / 客户端完整性 / 更大范围访问限制
     → 此时应停止采集、走官方客服，不要继续加请求
⑥ 页面看着正常、只有采集记录里"售罄"
     → 100% 先查解析层（空 skus 数组、OCR 空返回、dump 失败）
```

| 层级 | 影响面 | 本项目证据 |
|:--|:--|:--|
| 单商品 | 1 个 goods_id | 链路调研里个别商品 `skus` 空 |
| 单店铺 | 同 mall 多品 | 未在本机材料中查到明确样本 → **[未取证]** |
| **账号/会话** | **登录即全店售罄** | **本机 L119–L122 实测** ← 主人本轮现象 |
| 单设备 | 该设备上所有号 | 协议允许按设备信息关联；本机无干净对照 → **[推断]** |
| 网络出口 | 同出口多号 | 协议允许按 IP 交叉关联；本机无对照 → **[推断]** |
| 更大范围 | 平台侧故障/维护 | 协议 §一 4 承认系统维护/网络/程序漏洞可致服务异常；**[猜测]**，未观测 |

**关键限制**：本机**没有做过**「同设备不同号 / 同号不同设备 / 同号不同网络」的干净对照实验（外部资料 §四也建议不要靠多账号多设备反复试错，会扩大关联）。所以"设备级/网络级到底占多大权重"**保持 [推断]，不补空白**。

## §6 恢复与排查：不绕过平台限制的流程

**排查（只观察、不操作、不加重访问）**
1. 记录一次异常的完整上下文：商品链接/ID、店铺、SKU 规格、地区、时间、客户端版本、是否登录、是否所有商品异常、有无明确的限购/不可配送提示。**只截页面公开展示**。
2. 按 §5 判定树定位到"账号/会话"层就**停**，不要继续点、不要继续刷、不要用下单/领券/助力/拼团去"验证"——外部资料 §二 E 明确：把信息读取和交易活动混在一起，会把问题从读取升级成交易风控。
3. 先排除解析层（§3-07）：`skus` 是不是空数组、OCR 是不是返回空、dump 是不是根本没产出文件。
4. 保存证据后停止采集，走官方渠道：拼多多 App 在线客服 / 消费者 021-53395288（8:00–23:00）/ 商家 021-5339-5088（8:00–20:30）。〔**[事实]**，外部资料 §四，出处 [5]〕

**"合规恢复"要说实话**
- 官方**没有公开**"账号被限后自动解除的时间"或自助解限接口。任何"等 N 小时就好""清缓存洗白""改某个参数就恢复"都是 **[未证实传闻]**（外部资料 §三已逐条列过）。
- 能确定有效的只有两类：**① 停止异常访问 + 让账号回到正常人工使用节奏**（不再拿它做批量采集）；**② 把数据来源整体迁到授权通道**（§8），从根上不再依赖消费者账号的商品页可读性。
- 本机 L121 的"换号恢复"是**现象观察**，不是**恢复方案**——它验证了归因，但按 §3-06 的关联规则，多号轮换恰恰是扩大关联的动作，不写进建议清单。

## §7 【主人真正要的】怎么调，能少风控 —— 落地清单

### 7.1 三个杠杆，按收益排序

| 序 | 杠杆 | 为什么排这里 | 证据 |
|:--:|:--|:--|:--|
| **1** | **采集方式：自动点击 → 人工浏览 + 只读被动抄** | **直接把"非人请求"消掉**，与手动浏览同流量，这是唯一被本机验证过能一次拿全 105 SKU 且零点击零网络改动的路径 | 2.0 会话 L26；链路调研 §3.2「零新增请求」 |
| **2** | **行为节奏：拟人 + 限速 + 熔断** | 已经因"快进快出"把账号搞报警过一次；协议以"正常消费习惯"为异常基准 | 交接 §8 硬约束 + 实测拟人参数 |
| **3** | **账号卫生：单号单设备稳定环境，不切换、不多号共用** | 售罄=账号级；协议按交叉信息认定关联用户 | 本机 L121；官方协议 |
| 4 | 设备/root 层 | **优先不动**；本机隐藏实测反效果 | L134/L143/L145 |

> **一句话**：少风控 = **少发请求 + 发得像人 + 别让平台看到一堆号在同一台 root 机上串**。设备怎么打扮都是第四位。

### 7.2 关于「root 状态屏蔽掉」—— 给明确做法（不是加隐藏，是**减层**）

**判定：不再增加任何隐藏/伪装层。** 理由见 §0 结论 2 与 §3-04，本机三连实测已证伪。

建议按这个顺序收：
1. **保留 root + LSPosed 只读 hook**（这是采全图片/视频/SKU 字段的前提，去掉就退回"采不全"）。〔L125 本机 [事实]〕
2. **卸掉/停用会制造不一致的多余层**：Shamiko 之类白名单隐藏模块（本机已证卡死 PDD）、多开/分身、修改版客户端、与采集无关的常驻代理开关。原则是**环境越接近一台普通已 root 机越好，而不是"看起来像没 root"**。
3. **抓包代理只在取证窗口开，取完就关**，不要长期挂；别让"每 2 分钟自动拉起代理抢前台"的守护任务回来（2.0 会话 L59 已修过一次）。
4. **不为了采集去改系统参数、不改系统时间、不频繁清应用数据**（清数据会动登录/会话状态，§3 设备表已列）。
5. 若某次必须验证"是不是设备层"，**只做一次干净对照**，不要多号多设备反复试（外部资料 §四）。

### 7.3 拟人参数（直接用本机实测有效值，别自己另编）

来自 `pddsrc\交接-拼多多手机采集.md` §8，标注为「本会话实测有效」〔**[事实]**〕：

```
滑动    x=540±70, y1=1750±160, y2=y1-650~1150, 时长 230~500ms
停顿    滑动后 1.6~3.2s；点进商品后 9~12s；返回后 3.5~5s
单轮    1 次滑动 + 1 次点击，总时长约 1 分 46 秒
```

配套三条硬约束（同文件 §8）：不 OCR 截图取数、所有动作必须像人、**手机操作前先确认账号状态**。

再加两条工程闸门（**[推断]**，基于本机"快进快出把账号搞报警过一次"）：
- **异常熔断**：一旦出现「全店/多品同时售罄」「登录验证」「错误率突升」「账号提示异常」→ 立刻停，转人工，不自动重试。
- **失败退避**：请求失败不立即重放；重试次数设上限，超限停机。

### 7.4 把"主动采集"改成"被动抄"（收益最大的一处）

现有资产已经足够，不必新写系统：
- 数据权威源 `goods.entity.w.sku`，`setRenderResponse(w)` 一拿全量（链路调研 §1、§3.1）。
- **hook 只做"多读一次字段"**：不 hook 网络、不改返回值、不改字段、不构造请求、不点规格面板 —— App 自己发自己的请求，采集端零新增。〔**[事实]**〕
- 本机已验：105 条真实 SKU 一发即中、PDD 进程存活、零点击零网络改动。〔**[事实]**〕
- 界面侧已有「浏览即采（你点它抄）」模式（2.0 会话 L73 日志「系统就绪。两种模式：参数慢采（自动）/ 浏览即采（你点它抄）」）→ **把默认模式钉在"浏览即采"，把"自动连点慢采"降级为手动启动、且默认不上账号**。
- 传输走局域网 `http://<PC_IP>:18080/ingest` 本地接收，不保存 `AccessToken`/`pdduid`/cookie（链路调研 §4.3 第 5 条）。

这一处的本质：**风控看见的流量 = 一个正常人在慢慢翻商品**，而不是"一个程序在批量拉详情"。设备层再怎么调都做不到这一点。

### 7.5 账号卫生（针对"有些号一登进去就售罄"）

- **一号一机一环境长期固定**，不频繁退出/重登、不在多设备间切、不多号共用同一 root 机与同一出口。〔官方关联规则 + [推断]〕
- **已出现"登录即售罄"的号：停止拿它采集**，让它回到正常人工使用；不参与批量任务。〔**[推断]**，基于本机 L121 归因〕
- **不通过换号/轮换 IP/伪造设备去"试"解除** —— 外部资料 §四.3 明列，且会扩大关联用户范围。这不是绕不绕过的立场问题，是**实测无效且反效果**（§0、§3-06）。
- 采集与**领券/助力/拼团/下单/评价/退款完全隔离**，信息读取绝不混交易动作。〔官方协议 §二 E〕
- 每次采集留审计记录：授权来源、目的、字段范围、时间、请求量、错误率、删除情况。〔外部资料 §四.7〕

### 7.6 明确"不做"的清单（判据是无效/反效果，不是立场）

| 不做 | 判据 |
|:--|:--|
| 再加 root/环境隐藏层、装 Shamiko 类模块 | 本机 L143 卡死 PDD、L145 点进商品仍被风控 |
| 换号轮换、多号轮登来"绕开" | 本机 L121 只证明归因；官方按交叉信息关联，轮换扩大面 |
| 轮换 IP / 代理池 / 伪造设备参数 | 官方关联规则 + 外部资料列为未证实传闻 |
| 抓包重放、构造 `render` 请求、解 `libpnet.so` 封装 | 链路调研 §6 已判「数天–数周、高风险、不建议」；且属构造请求 |
| 用固定"刷新 N 次/间隔 N 秒"当安全阈值 | 网上固定数字 = [未证实传闻]，本机实测值是**节奏区间**不是阈值 |
| 靠下单/领券验证是否恢复 | 会把读取问题升级成交易风控 |

## §8 长期解：把数据源迁出消费者账号

外部资料 §四.4 的方向与本项目并不冲突，且是**唯一能把风控变量归零**的路：

- 拼多多开放平台面向**商家 / 企业 ERP / 打单发货 / 进销存 / 商品 / 交易 / 物流**提供开放能力与开发者认证路径。〔**[事实]**，出处 [3]；⚠ 本轮 `open.pinduoduo.com/application/document/api` 为 SPA，只回标题，**具体 API 清单与授权粒度 [未取证]**，需下轮带认证后核〕
- 若主人身份是商家/品牌方/获授权服务商 → 走开放平台或商家后台导出，**不要拿个人消费者账号当批量采集凭证**。
- 数据最小化：只留业务必需的公开商品字段；避免买家姓名、手机号、地址、支付、聊天、设备标识、精确位置；设保存期限与删除机制。〔外部资料 §四.5，法条 [4][6]〕
- **现实折中（[推断]）**：8.0 那条线要的是「采集到的商品视频 + 详情字段」，这些字段**本机只读 hook 已经能拿全**，无需迁 API；开放平台更适合作为**后续批量化、194 条历史视频处理**之前的合规兜底，而不是当前 P0/P1 的前置。
