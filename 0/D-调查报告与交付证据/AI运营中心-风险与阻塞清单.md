# AI运营中心 - 风险与阻塞清单

> 结论等级：**C（重大风险，不建议现在全面开工）** —— 风险不在技术，在**平台侧不确定性与不可自动化边界**。
> 证据标注：`[源码确认]` / `[本机实测]` / `[官方文档]` / `[设计建议]` / `[尚未验证]`

## 结论摘要（≤200 字）

7.0 的**技术风险可控**，**业务风险不可控**。三个必须接受的现实：
① 抖店没有免签 API（`dd.py` 首段自述），所有抖音侧动作只能走浏览器 → 稳定性受页面改版支配；
② 视频号发布/商品关联的授权与权限未核实 → 可能整条链路只能人工点；
③ 平台风控与验证码**不许自动绕过**（主人红线）→ 一旦触发，任务必须停下等人。
**最容易把项目做废的不是技术，是"什么都想自动"，最后每个环节都卡在一个需要人点的按钮上。**

## 三、业务与运营风险（最容易被低估的一类）

| # | 风险 | 说明 |

| **O1** | 「什么都自动」= 每个环节卡一个人工按钮 | 活动报名、达人洽谈、价格调整、内容审核在平台上大多有**人工确认环节**。7.0 的正确目标不是「无人」，是「把人的动作从 20 次压到 3 次」。**这条要写进验收标准，否则永远验收不过** |

## 四、不可做的事（红线，写死在代码里，不做成配置项）

1. 不做自动绕过验证码 / 人脸 / 短信验证 / 平台风控。
2. 不去水印后当原创素材；`authorized=0` 的素材禁止进发布队列。
3. 不在未获批的情况下自动改价、改活动价、改佣金、加广告预算。
4. 不在初期自动**正式发布**抖音视频（只能备料到待发布）。
5. 不批量删除商品（L4，只有人能点）。
6. 不把 AppSecret / Cookie 明文写进库、日志、报告。
7. 不复制第二套商品库，不重写 1–6.0 的稳定链路。
8. 不在缺 API 权限时伪造数据（`source` 必填，`unknown` 就写 `unknown`）。

## 五、失败模式（这类项目最典型的四种死法，先把话说在前面）

| 死法 | 症状 | 预防 |
|:--|:--|:--|
| **建了表没人写** | 新表 0 行，像 `v3_task_log` 一样躺几个月 | P0 验收强制「表里有 ≥6 行真实状态」 |
| **静默降级** | 6.0 挂载失败只写日志不崩（`[源码确认]` `main_window.py:249-251`）→ 用户以为功能在跑 | 7.0 启动/失败必须上界面红点 + 写 `ops_browser_error` |
| **报成功但没干成** | 计划任务 `Last Result 0x0` 而实际拒绝开跑（本项目 04:00 整理任务已踩过，见铁律 18） | 只认目标自证：队列状态 + 库里行数 + 页面截图 |
| **验收靠接口 200** | 页面点不开、按钮没反应，但 API 回 200 | 铁律 21：ego lite 真点一遍才算验收 |

## 六、待主人决策（只有 3 件，其余由我判断）

1. **是否申请抖店开放平台资质/权限**（决定抖音侧是「全浏览器」还是「能部分走 API」）。
