## 零、先决判断（如果只读一段，读这段）

**「采集抖音小店网站后台结构数据」这个需求，有一半应该丢掉。**

| 原本的意图 | 实际该怎么做 | 为什么 |
|:--|:--|:--|

## 一、硬门槛：抖店自研比微信小店重得多（必须先告知主人）

| 项 | 微信小店（已实测） | **抖店（本文档对象）** |
|:--|:--|:--|
| 入口 | 后台 → 服务市场 → 经营工具 → 自研 | **抖店开放平台** `op.jinritemai.com` → 注册开发者账号 |
| 审核 | **无审核，填了就有** | **有审核：1–3 个工作日** |
| 资质 | 无 | **系统功能说明书 + 软件著作权证书**（著作权人须 = 开发者账号认证主体）+ 功能截图 + 源码片段 |
| 首次建应用 | — | **必须选一个自有店铺完成授权**，后续加店铺走「控制台 → 授权管理」 |
| 凭据 | AppID + AppSecret | client key + client secret，权限勾选后逐个审批，**被驳回可单申请，5 工作日内，最多申请 5 次** |

**结论一句话**：抖店这条路**卡在软著**。没有软著就先启动申请（软著办理周期长），
期间用第 1、2 块顶上，**不要因为等资质而停工**。

**必须向主人确认的一件事**：手上有没有**已登记的软件著作权**（主体与店铺营业执照一致）。

## 二、第 1 块 · 规则文档库（当天可完成，优先级最高）

**性质**：公开网页，无需登录。**这是三块里唯一零风险、零依赖的。**

### 采集对象

| 类别 | 出处 | 要采什么 |
|:--|:--|:--|
| 平台规则正文 | 抖店规则中心 / 学习中心（`school.jinritemai.com/doudian/web/article/...`） | 规则标题、文号、生效日期、**失效/被替代关系**、正文全文 |
| 体验分规则 | 同上 | 三大维度权重、出分门槛、考核窗口、扣分项、剔除项 |
| 违规与处置 | 同上 | 违规类型、处罚阶梯、申诉入口与时限 |
| 活动/准入 | 同上 | 精选联盟准入、头部创作者门槛、类目准入 |
| 公告 | 后台公告栏（需登录） | 接口变更公告（**这条最要紧：接口变了不改造会静默失效**） |

### 交付物

```
rules/
  index.json          每条规则：id / 标题 / 生效日 / 失效日 / 替代关系 / URL / 抓取时间 / 内容哈希
  md/<id>.md          正文（转 Markdown，保留表格）
  changelog.md        同一规则的历史版本差异（只记 diff，不存全文）
```

### 三条硬要求

1. **必须存「生效日期 + 失效日期 + 被谁替代」**。规则会改，只存正文 = 三个月后无法判断哪条还有效。
2. **必须存内容哈希**。下次抓到哈希没变就不重写，避免无意义 diff。
3. **必须区分「规则」与「解读」**。第三方文章（含本任务书引用的二手来源）一律标 `[二手·未核]`，不得当规则原文用。

### 已知的规则口径差异（**这是最容易踩的坑，必读**）

主人同时在微信小店和抖店开店，**两家的体验分口径完全不同，不许混用**：

| 项 | 微信小店（已核） | **抖店（二手来源，待核）** |
|:--|:--|:--|
| 更新频率 | 每天 12:00 | 待核 |
| 考核窗口 | 近 30 天滚动（T-30 ~ T-1） | 近 30 天 |
| 出分门槛 | 有效支付订单 **≥10 单** | **≥30 单** |
| 权重 | 服务 50 / 商品 30 / 物流 20 | **商品 40 / 物流 25 / 服务 35** |
| 新店初始分 | 无 | **71–78 分区间** |

> 抖店那列来自二手文章（蝉妈妈、CSDN 等），**未经官方原文逐字核**。第 1 块的第一件事就是把它核准。

## 三、第 2 块 · 后台 UI 地图（只做 API 覆盖不到的）

### 只采这四类，别扩张

| # | 页面 | 为什么必须爬（API 覆盖不到） |
|:--|:--|:--|
| 1 | **店铺诊断 / 体验分详情** | 诊断结论是页面渲染的计算结果，接口通常不给分项依据 |
| 2 | **违规中心 / 申诉** | 申诉是强交互流程，接口一般不全 |
| 3 | **活动报名** | 报名资格与规则跳转在页面上，且经常改 |
| 4 | **公告栏** | 接口变更通知只在这里 |

### 采集方式（沿用本机已验证的浏览器纪律）

**只用 ego lite**（本机唯一浏览器入口，见 `AGENTS.md`）。**不许启 Chrome / Edge / Playwright / 无头浏览器。**

```
① 主人在 ego 里正常登录抖店后台（我不碰密码、不碰登录态）
② 我用 task.page() 读页，只读不点
③ 每页产出：页面标题 / URL / 面包屑 / 表格列名与首行样本 / 表单字段名 / 按钮文案 / DOM 结构指纹
④ 落盘后立刻算结构指纹；下次比对指纹变化 → 页面改版预警
```

### 抗改版写法（这是本块的唯一技术难点）

抖店后台的 class 名是编译混淆的随机串（`_a1b2c3` 这类），**今天这样明天可能变**。
所以定位一律**按文本 / 按结构 / 按相邻关系**，**严禁写死 class 名**：

```js
// 好：按可见文本找，改版也能活
[...document.querySelectorAll('a,button')].find(e => e.textContent.trim() === '查看详情')

// 坏：写死混淆类名，下周静默失效且不报错
document.querySelector('._a1b2c3 > div:nth-child(2)')
```

**判据**：写死的选择器一旦失效，程序**不报错、只返回空** —— 这是最危险的失效形态（同族教训见 `AGENTS.md` 铁律 18「虚假的成功信号」）。

### 后台结构的核心字段（从微信小店同类系统迁移的经验，抖店需实测校正）

```
店铺信息        店铺 id / 名称 / 主体 / 类目 / 状态
商品            id / 标题 / 三级类目 / 主图 / 详情图 / SKU 列表 / 价格（★单位必核）/ 库存 / 上下架状态
订单            订单号 / 状态 / 金额 / 买家（脱敏）/ 物流 / 售后
体验分          总分 / 三维分 / 各项指标 / 考核窗口 / 扣分原因
```

★ **价格单位必须实测确认**（分 / 元）。微信小店实测 `sale_price 98000` 应为「分」，但**未逐字核文档**。
抖店若单位不同，价格会差 100 倍 —— **写任何代码前先用一件真实商品对账**。

## 四、第 3 块 · 官方 API 能力清单（先启动申请，后干活）

### 流程（官方文档口径）

```
① op.jinritemai.com 注册开发者账号 → 实名认证
② 申请类目资质：系统功能说明书 + 软著 + 功能截图 + 源码片段   ← 1–3 工作日
③ 创建应用：选应用业务类型（自用型 / 通用型）+ 应用类目 + 完善信息
   ★ 首次申请自研应用，必须选一个自有店铺完成授权
④ 提交后系统自动审核 → 通过 → 控制台拿 client key / client secret
⑤ 勾选所需权限，逐个填申请理由（被驳回可单申请，5 工作日内，最多 5 次）
```

### 签名（**待核，先别写死**）

二手文章称抖店签名是「参数按字母序排序 + MD5」，形如
`md5(app_secret + 排序拼接串 + app_secret)`。
**官方签名算法页在 `developer.open-douyin.com` 的 OpenAPI 文档「签名算法」条目下，开工第一件事是读它逐字核对**，
不要照二手文章写代码。

### 必须先摸清的能力

```
商品：列表 / 详情 / 创建 / 编辑 / 上下架 / 类目树 / 属性 / 图片上传
订单：列表 / 详情 / 发货 / 售后
库存：查询 / 同步
体验分：查询（能否拿到三维分项 + 扣分原因 —— 这决定第 2 块要不要爬）
素材：图片 / 视频上传
消息：订单变更、商品审核结果（推送）
```

## 五、红线（不许做）

1. **不许把「爬后台 UI」当主线。** API 能做的，一律走 API。
2. **不许写死混淆 class 名。** 一律按文本 / 结构定位。
3. **不许对真实店铺发任何写操作**（改价、改库存、上下架、发货）—— 除非主人明确指定用哪一件商品试，且能一键还原。
4. **不许把 client secret / access_token 写进代码、配置文件、截图、聊天记录。** 只放本机环境变量。
5. **不许把二手文章当规则原文。** 引用必须标来源与「是否已核」。
6. **不许把微信小店的参数直接套到抖店**（体验分权重、出分门槛、价格单位、签名算法全不同）。
7. **不许用「HTTP 200」当验收。** 必须核到具体字段值。
